# Customer signup without GitHub

User outcome: customers can create an account with email/password or Google, open their dashboard, and share a demo/request before deciding whether to connect GitHub. Existing GitHub accounts, projects, and operator access continue working. GitHub repository access remains read-only and explicitly connected after signup.

In scope: verified email/password signup and sign-in, one-time email verification and password recovery, Google authorization-code sign-in with state/PKCE/nonce and signed ID-token validation, existing GitHub sign-in, safe identity linking for a signed-in customer, secure account-session rotation/logout, honest provider configuration states, and customer labels that work without a GitHub username. Backoffice authorization remains the existing verified numeric GitHub operator allowlist; email/Google signup grants no operator role.

Acceptance:

- Customer sign-in presents email/password and configured Google login, with clear Create account / Sign in / Forgot password actions. GitHub remains available to existing customers. Account signup requires no repository installation.
- Email signup sends a verification link through the configured mail provider. Unverified credentials cannot open protected project APIs. Links are hashed, expire, and are consumed once. Password recovery gives the same public response for existing/nonexistent email addresses, and reset revokes every account session and connected review credential.
- Google requests only openid/email/profile and validates issuer, audience, expiry, signature, nonce, and verified email. It never merges an existing account merely because an email matches; linking requires a current signed-in account and fresh provider authorization.
- Google can create an account directly for a Gmail or signed Google Workspace hosted-domain identity. Other Google email providers first use verified email signup, then explicitly connect Google from that signed-in account. An existing GitHub-only account cannot verify a non-hosted email by creating a second account; Account settings offers a hosted identity or support instead.
- A known Google subject whose email changes keeps its original projects. The old recovery email, password, challenges, sessions, and repository credentials are retired. A new authoritative, unclaimed email becomes the recovery address; conflicting or non-hosted addresses leave recovery disabled with persistent support guidance. A bounded unique-conflict retry handles a concurrent claim, and issuance checks the requested destination under the account lock.
- An unverified signup stores credentials only in the verification challenge; confirming a link activates that challenge's password/name. Resending requires the matching pending password and does not reactivate an earlier signup's credentials.
- GitHub repository connection can bind a GitHub identity to an email/Google account only after authenticated OAuth, without switching project ownership or taking an identity already attached to another account. Existing identity mismatch protections remain enforced.
- Switching accounts clears the previous browser's repository credentials and saved inspection selection. Auth and token issuance have both network and identity throttling. Passwords, provider credentials, tokens, and private project data never appear in public response metadata or logs.
- Provider configuration is explicit. Production cannot claim a sent verification/reset email without an enabled delivery adapter. Google credentials and sender configuration are dedicated to m8itwork; no other project's secrets are copied.
