# Independent operating setup

Outcome: detect API/database failures independently of Railway and detect a stopped backup host; keep encrypted, restorable off-provider database copies. Reviewed operating milestone `57c1f22c424957aeb2c647f7bc76e28b095e0ddf` supplements deployed application milestone `fb84740`.

Scope: a portable private Docker backup agent (PostgreSQL 18 client, read-only database principal, no application/worker/payment credentials); a Cloudflare scheduled Durable Object watchdog; private, authenticated heartbeats/status; bounded health and delivery attempts; durable, generic failure/recovery notifications. No source/customer content is sent to the monitor. Backups run on startup when due and every 20 hours, retry hourly after failure, and retain the newest 14 successful archives. A backup is published atomically only after encryption completes and disk sync succeeds. Failed archive creation never advances freshness or prunes successful archives. Retention runs only after a new durable archive exists; state-write failures preserve the previously reported timestamp and retry hourly.

Acceptance: meaningful failure/rotation/restart/idempotency tests; container isolation and actual encrypted production snapshot; isolated authenticated restore; deployed independent scheduler and protected status; latest backup within 24 hours; controlled owner alert/recovery receipt when authorized. An external monitor detects a missing host after 10 minutes and backups older than 24 hours. Three consecutive one-minute API failures open an incident. Keys need a separately recoverable private copy. A sleeping Mac still misses backup execution; the watchdog reports this, it does not create backups remotely. Continuous backup RPO requires moving the same container to an always-on host.

Exclusions: production database replacement, automatic refunds/charges, live merchant activation, changing the owner's password, and pretending cached login or test fixtures are fresh provider acceptance. Owner actions remain named dependencies. Staff Engineer and Product Owner review the completed operating implementation; Designer is not applicable because this change introduces no product UI or customer workflow.

## Private installation and incident handling

Store a mode-0600 JSON file outside the checkout with `databaseUrl` (dedicated read-only role; `sslmode=verify-ca` or `verify-full`), `databaseCa` (the server CA/certificate obtained through the provider's authenticated console/SSH), `encryptionKey` (32 random bytes, base64), `monitorUrl` and `heartbeatToken` (32+ random characters). Save the encryption key and application encryption key in separately recoverable private storage; losing both the host and its only key copy prevents recovery. Never put any of these in shell arguments or commit them. A database role must only have CONNECT, schema USAGE and table SELECT, with future SELECT defaults granted by the actual migration owner. It must not be a superuser, bypass RLS or have write privileges.

Set `M8_OPS_CONFIG` and `M8_BACKUP_DIRECTORY` to private absolute host paths, then `docker compose -f compose.ops.yml up -d --build`. Keep both outside the checkout and Railway. On Linux, the mode-0600 configuration file and private archive directory must be owned by container UID 10001; Docker Desktop host mounts require checking access on that host. There are no exposed agent ports or Docker socket mounts. Only one agent may use a directory. Inspect `docker compose -f compose.ops.yml logs --tail=30 backup` for generic codes; start/restart the container after repairing configuration/storage. Failed-state persistence retries hourly, even when a valid archive was published. Partial files are not retention candidates; investigate then remove only an abandoned agent-owned partial, never successful archives.

Deploy the Cloudflare monitor with `npm --prefix ops ci` and `npm --prefix ops run monitor:deploy`. Supply `HEARTBEAT_TOKEN`, `RESEND_API_KEY` and the private owner destination `ALERT_TO` using Wrangler secret stdin. Keep the destination outside tracked config. Start with `ALERTS_ENABLED=false`; enable only after the new API `/health` returns `{status:"ok",recovery:false}`, a valid backup heartbeat exists and owner alert tests are authorized. The old release does not expose this health contract. Sampling is every minute; three consecutive failures mean approximately 2–3 minutes to detection plus mail dispatch, not a guaranteed one-minute delivered alert.

Protected `/status` uses the same heartbeat token in an Authorization header. Read it through a private script/config, never a browser URL or shell argv. It returns only backup/heartbeat times, incident kinds and pending/uncertain alert IDs. Check this monitor directly during API outages; the backoffice does not represent independent host incidents. API incident: inspect Railway API/database health, pause collection if uncertain. Host incident: wake/start Docker, verify connectivity. Backup incident: inspect disk/tool permissions/newest archive and retry by restarting; retain the last good copy. Recovery is notified once the condition clears. `/probe` queues a fixed generic test failure/recovery pair without changing production or accepting arbitrary recipients/URLs. Uncertain alerts older than 23 hours need checking Resend history; no automatic fresh-key resend is permitted.
